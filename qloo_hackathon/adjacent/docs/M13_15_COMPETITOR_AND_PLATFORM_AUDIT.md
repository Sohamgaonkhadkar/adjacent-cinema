# M13.15 — Competitor, Rubric & Platform Audit

**Snapshot:** 19 October 2026 | **Scope:** the current Adjacent Creator product, its reviewed competitors, the Qloo hackathon rubric, active persistence/state, and model/training readiness.

## Executive decision

Adjacent's strongest reviewed-set position is **measured cross-domain cultural evidence → a falsifiable film-positioning bet → a saved experiment → append-only observations/evaluation**. That differs from the creator tools reviewed here, which focus on discovery/SEO, packaging tests, or post-publication channel analytics. This is a relative position within the repository's reviewed set—not proof that no other product does it.

The three evidence-backed product improvements in this sprint are:

1. Surfaced sanitized per-seed resolution evidence (verification status/method, Qloo year/name/entity ID, verification notes, and call IDs) through the API and Creator UI, without exposing raw Qloo response bodies.
2. Corrected the append-only evaluation chain so each new evaluation supersedes the current history leaf and the experiments list reports that current outcome; added experiment-local validation for observation evidence and correction links.
3. Changed Qloo request pacing from per-client to per-Qloo-key **per backend process**, so concurrent runs in one worker share the configured limit. This is not a distributed limiter.

No Qloo query parameters, affinity scales, candidate-selection rules, or model decisions were changed: the existing code already has strict parameter allowlisting, title/year identity checks, and context-local score comparability, while there is no live Qloo response in this runtime with which to validate a changed request shape.

**Production status remains blocked:** this checkout has no `DATABASE_URL`, PostgreSQL service/client/container runtime, migration framework, or verified deployment. SQLite has not been partially migrated; the live Creator run has not been tested with the user's rotated key.

### Competitive conclusion

**[CODE FACT]** Creator Mode accepts a working film title and creator context, resolves the submitted comparable works/themes as Qloo seeds, produces an evidence-linked Positioning Bet and Test Card when evidence suffices, and can save an experiment. The working title is context; it is not itself assumed to be a known Qloo film. The result explicitly shows which seeds resolved and excludes unresolved seeds from evidence.

**[INFERENCE]** The defensible distinction is not “better YouTube growth” or “more accurate view prediction.” It is the *decision lifecycle* connecting Qloo cultural affinity to a testable positioning choice and later observations. TubeBuddy is the nearest reviewed overlap on tests; vidIQ/Viewstats overlap on creator workflows and analytics; MUBI is viewer-facing. The claim “no reviewed tool connects all four stages” is bounded to these named products and sources.

**Limits:** this product does not verify distribution rights, festival eligibility, title availability, audience demand, views, retention, revenue, or causal lift. Qloo affinity is similarity evidence, not a forecast. The repository contains no customer-adoption or business-impact result for Creator Mode.

## Persistence and process-local state audit

| Component | Active role and storage | Multi-worker / deployment consequence |
|---|---|---|
| `app/domain/experiment_repository.py` | **Active** Creator experiment, observation, and evaluation store. SQLite at `ADJACENT_EXPERIMENTS_DB`, default `data/processed/experiments.db`; schema is created with `CREATE TABLE IF NOT EXISTS`; runtime file is ignored by Git. One connection and `RLock` per process. | Persists across restarts only if the same local file survives. The lock is process-local; there is no Postgres adapter, migration chain, connection pool, or cross-host durability. Do not treat a shared/ephemeral deployment filesystem as a production store. |
| `app/domain/youtube_auth.py` + `app/api/youtube_routes.py` | **Active but explicitly single-connection.** SQLite at `ADJACENT_YT_TOKEN_DB`, default `data/runtime/youtube_auth.db`; one OAuth credential row and persisted one-time OAuth states. Other findings:

- No `DATABASE_URL` adapter, PostgreSQL schema, migration directory/Alembic config, or PostgreSQL CI service is present. Active SQLite schemas initialize inline; the older outcome repository has in-code schema evolution, not a shared migration system.
- Runtime `experiments.db` and `youtube_auth.db` were not present in this checkout. The only discovered SQLite database is the tracked outcome-ledger file above.
- There is no deployment manifest, verified hosted URL, or evidence of persistent cloud storage in this checkout. Existing deployment ADR `docs/adr/006-deployment-topology.md` already marks deployment as proposed, not verified.
- Qloo pacing is per process, while public quotas and run state are also process-local. Background run tasks are not restart-safe. These are explicit multi-worker blockers, separate from the experiment database.

### PostgreSQL decision and exact blocker

**No migration was attempted.** At audit time the environment has no `DATABASE_URL`, `psql`/`postgres`/`pg_ctl`/`pg_isready`, Docker/Podman, or provisioned PostgreSQL instance. There is therefore no actual PostgreSQL service against which to test connection behavior, schema migrations, transaction/idempotency behavior, append-only corrections, zero-versus-missing values, or lifecycle parity. Adding a driver and unverified SQL would be a half-migration and violate the acceptance bar.

SQLite remains the current local implementation and local test backend; this is **not a claim of PostgreSQL support or production-ready multi-worker persistence**. To resume safely, first provide a reachable test PostgreSQL instance and secret-managed `DATABASE_URL`, then design/version migrations, port repository semantics without duplicating business rules, and run integration tests for restart/lifecycle, provenance, idempotency, correction chains, append-only history, and observed-zero versus unavailable. Separately replace/coordinate `RunStore`, OAuth ownership/token handling, and process-local limits. No production claim should precede those tests.

## Qloo, deterministic logic, LLM, and training

- **Qloo is an external API, not a locally trainable model in this codebase.** Do not fine-tune Qloo or claim training its model.
- **Deterministic decision engine:** the agent is an explicit state machine with bounded tool calls. Candidate resolution checks exact normalized title and year; mismatches/ambiguous records are not silently promoted to verified results. The cohort ranker scores a slate per query/domain and avoids comparing raw affinity values across different normalization contexts. The UI calls affinity similarity—not popularity or demand.
- **Evidence and feedback:** run traces retain source/data status and call IDs; investigation references are checked against that run; experiment corrections are append-only. This sprint additionally validates experiment-local evidence references and current correction targets.
- **LLM role:** optional Role-B prose synthesis of the already-structured investigation. It has no Qloo tools and is not the source of candidate identity, affinity, geography, or ranking. Output is schema-checked, claim references are validated, forbidden performance/causality claims are screened, and a deterministic fallback is explicitly labelled. Structural reference validity does not prove semantic support; that limitation is documented in `app/domain/synthesis.py`.
- **Training is not justified now.** The tracked Cinema ledger has zero outcome-measurement rows, and the active Creator runtime experiment database was absent; there is no Creator-labelled dataset, defined training objective, baseline, or held-out evaluation set in this checkout. Appearance-only training would be unjustified. Improve deterministic identity resolution, validated query construction, per-context scoring, evidence checks, and lifecycle tests first. Consider a learned component only after consented labels, a predeclared decision objective, adequate sample size, temporal and creator/film holdouts, a baseline, and a measured evaluation metric exist.

## Secure live Creator acceptance run (not executed in this sprint)

Use only the user's rotated key in the trusted local Antigravity **backend** environment. Never put it in this repository, the browser, a frontend variable, a test fixture, chat, command output, or logs. The backend reads `QLOO_API_KEY` from its process environment; a plain `.env` file is not automatically loaded by the app unless the trusted launcher loads it. Leave `QLOO_BASE_URL` unset (default) or set it only to `https://hackathon.api.qloo.com`.

1. Inject the key through the trusted local secret/environment facility, then start the backend so that process inherits it. From `qloo_hackathon/adjacent`, run `make run`; the backend listens on port 8000. Check `GET /health` for configuration/mode only—do not print or inspect the secret value.
2. Start the frontend in `qloo_hackathon/adjacent/frontend` with `ADJACENT_API_ORIGIN=http://127.0.0.1:8000 npm run dev` (or the local Antigravity equivalent). Browser calls stay on relative `/api`; the Next server proxies to the backend. Open `/creator`.
3. Fill in a **working title** plus optional logline, genre, language, themes, release goal, and 2–3 comparable works with their known years. For a controlled resolver check, use a well-known reference such as **Parasite (2019)** or **Get Out (2017)** if Qloo returns it. The working title is not assumed to be a catalogue entity; the comparable works/themes are the Qloo-resolved seeds. Leave release location blank for the first run to avoid making geography a required condition.
4. Click **Analyse cultural position**. Do **not** click “View labelled fixture demo (offline).” Wait for the run to finish. In “What was analysed,” confirm each reference's resolved/unresolved state. A valid resolution displays `VERIFIED` plus the expected Qloo name/year, entity ID, and resolution call ID(s); in the response these are under each item's `resolution_evidence` (`match_status`, `qloo_year`, `qloo_entity_id`, `call_id`, and `related_call_ids`). An unresolved, ambiguous, or mismatched seed must remain excluded. If the sample is absent or year-conflicted, report that outcome and use another known reference—do not substitute a fixture or guess.
5. Inspect the evidence panel and run response. For a successful live run, `result.data_status` and `result.investigation.data_status` should be `measured`; `result.programme.resolved_count` should reflect verified seeds. The referenced `call_id`s in `result.investigation.provenance.call_ids` must occur in the run trace. `GET /run/{run_id}/trace` should show real Qloo calls with `source: "qloo"`, `data_status: "measured"`, successful HTTP statuses, and no `source: "mock"` rows. Each seed's `resolution_evidence.call_id` must also be present in that trace. A measured label alone is not proof: inspect the actual successful trace rows and resolved identity.
6. Read FACT versus INTERPRETATION, limitations, and the Positioning Bet/Test Card. Do not interpret Qloo affinity as views, retention, revenue, attendance, or causal effect. Save the Test Card as an experiment from the UI if the run has a defensible hypothesis; the saved record should retain the source run and evidence references. Observations/evaluation are optional for the initial live smoke test.
7. If the run fails, preserve the exact `run.error` and trace error `kind`, `status`, and `retryable` fields. Do not relabel an API failure as a resolution miss or a successful live run. Expected classification: `401/403` is authentication/host configuration; `/entities` `404` is an entity-not-found data outcome; `429` is rate limiting (observe `Retry-After` where present); `5xx` and timeouts are upstream/transport errors. Public-demo mode intentionally sanitizes detailed upstream messages; use the trusted local backend for accurate diagnostics.

**Acceptance remains pending** until a real request with the user's secure local key completes and its resolved identity, successful Qloo trace, and evidence references are inspected. No live request or key was used for this audit.
